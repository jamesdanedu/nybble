# Nybble as a PWA

**What was built: an installable app shell. Not an offline app.**

Installed on a phone or a Chromebook, Nybble gets a home-screen icon and opens
without browser chrome — one less row of distractions in a lesson, one less
address bar to wander out of. It does not keep working when the network drops,
and this file is mostly about why not, because that is the part someone will
otherwise try to "fix" in a week's time.

---

## The finding

A runner is mounted in an iframe sandboxed **without** `allow-same-origin`
(`runner-host.js`, and the reasoning is in `runner-contract.md`). That gives the
runner document an opaque origin — and **an opaque-origin document is not
controlled by a service worker.**

Measured, offline, with the subresource already sitting in the worker's cache
(`node test/sw-sandbox-spike.mjs`):

| iframe sandbox | subresource arrives? |
|---|---|
| none | **loaded** |
| `allow-scripts` — what the portal uses | **FAILED** |
| `allow-scripts allow-same-origin` | **loaded** |

The frame's own navigation *is* served from the cache — that request belongs to
the parent page, which is controlled — so the runner document loads and then
fails on everything it asks for: `runner.css`, `runner-sdk.js`, and the ~950 KB
of Skulpt that `pyrun` needs. A student offline would get an activity that
half-appears and then does nothing, which is worse than a page that says
"you are offline".

This extends the opaque-origin table in
[`runner-contract.md`](runner-contract.md#what-the-sandbox-permits). That table
already says a runner cannot cache anything across loads. The sharper statement
is that **nothing else can cache for it either.**

The only sandbox that fixes it is the one the contract forbids, and for good
reason: `allow-same-origin` would give every runner the portal's Supabase
session. An offline lesson is not worth a student's activity code being able to
read their classmates' rows.

## Three other things would have to change anyway

Even if the sandbox problem vanished tomorrow:

1. **Every portal page is server-rendered per request.** `app/page.tsx` is
   `force-dynamic`; the session is a Supabase cookie read on the server;
   `/dashboard` and `/attempt/[id]` query Postgres before any HTML exists.
   There is no client-rendered shell to cache — offline, there is a fallback
   page and nothing else.
2. **Marking is server-only by design.** `attempt-client.tsx` posts to the
   `score` Edge Function precisely so that the browser never holds an answer
   key. Offline submission could only ever mean *queueing*, and queueing
   collides with rules the portal already enforces: first answer counts,
   `attempt already submitted`, and `time_limit_secs`. A queue that replays into
   those is a queue that loses work while claiming not to.
3. **iOS installs get their own cookie jar.** A student signed in in Safari is
   signed *out* in the installed app and lands on `/login`. With
   `NEXT_PUBLIC_SCHOOL_SLUG` usernames that is survivable, but it will generate
   questions on day one — worth saying out loud to staff rather than letting
   them discover it.

## What is actually here

| | |
|---|---|
| `app/manifest.ts` | `display: standalone`, `start_url: /dashboard`, icons. Claims nothing about offline. |
| `public/sw.js` | The worker. Read its header comment before adding a rule. |
| `components/service-worker.tsx` | Registration. Production only — a worker holding `/_next/static/` fights hot reload. |
| `app/offline/page.tsx` | The one page the cache keeps. |
| `public/icons/` | Generated by `scripts/make-icons.mjs`. |
| `test/pwa.test.mjs` | Manifest, registration, offline fallback, and what the cache is allowed to hold. |
| `test/sw-sandbox-spike.mjs` | The measurement above, re-runnable. |

### Two rules the worker follows

**Nothing belonging to a student is cached.** Not the dashboard, not an attempt,
not `/login`. School devices are shared, and a cached page outliving a sign-out
is a page the next student can read. The cache holds content-hashed build
output, the icons, and the offline notice — that is the whole list, and
`test/pwa.test.mjs` fails if anything else appears in it.

**Documents are network-first.** A stale assignment list is worse than no
assignment list: a student who acts on yesterday's dashboard wastes a lesson.
Falling back to `/offline` under the URL they asked for means "Try again" is a
plain reload that lands them where they meant to go.

`/runners/`, `/demo.html` and `/harness.html` are on the skip list — the worker
treats them as if it were not installed. Precaching them is the tempting fix
that does not work: it would spend a megabyte of a student's storage quota to
change nothing at all, for the reason at the top of this file.

## What would make offline genuinely possible

Not recommended, but so the next person does not have to re-derive it. Offline
activities need runners that ship as **one self-contained HTML file with no
subresources** — the frame's navigation is cacheable even when sandboxed, so a
runner with nothing to fetch would work. That means inlining `runner-sdk.js` and
`runner.css` into every runner, giving up the stable shared URLs that let a
runner be updated without a portal redeploy, and inlining Skulpt into `pyrun` at
roughly a megabyte per copy. It also does nothing for the three problems above:
the page around the runner still cannot render, and the answer still cannot be
marked.

That is a rewrite of the runner contract to buy partial offline support for the
activity box alone. It is written down here so the trade is visible, not because
it is worth making.

## Running it

The worker only registers in production, so `next dev` will not show any of
this:

```bash
npm run build && npx next start -p 8102
BASE=http://127.0.0.1:8102 node test/pwa.test.mjs
node test/sw-sandbox-spike.mjs          # self-contained, needs no server
```

Regenerate the icons after changing the art in `scripts/make-icons.mjs`:

```bash
node scripts/make-icons.mjs             # writes public/icons/
```
